# Worklist (F-24 / F-25 / F-26) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the List Report into a worklist: five views over one table with counts (Meine Arbeit, Fehler, Klärung, Freigabe, Alle), two new columns ("Wartet seit", "Nächster Schritt") whose texts come from the service, a priority-based default sort (errors first, then longest waiting), an error-aware row highlight, the recommended step as a header data point on the Object Page, and — new scope — the **reason of the release decision** (`releaseReason`, code list, limit) visible in the list and on the Object Page.

**Architecture:** Backend decides everything (CLAUDE.md rules 5/7): a stored `waitingSince` timestamp (set by the step dispatcher on every state change), virtual `waitingText`/`nextStep`/`nextStepText` filled in the existing after-READ handler next to the `can*` flags, calculated `priority`/`rowCriticality` on the DB (same pattern as `statusGroup`), and a stored `releaseReason` + `releaseLimit` written by the status machine's release check (code list `ReleaseReasons`, pattern `ReleaseStates`). Frontend is annotations + manifest only: five `UI.SelectionVariant`s, one unqualified `UI.PresentationVariant`, three `UI.DataField` columns, one `UI.DataPoint`, two fields in the Freigabe group, and `tableSettings.quickVariantSelection` in the manifest. No new custom UI code.

**Tech Stack:** CAP 9.9.3 (SQLite in-memory), SAPUI5 1.148.12 `sap.fe.templates`, Jest 30, OPA5 via `sap/fe/test` + `ui5-test-runner`.

**Spec:** CLAUDE.md; `docs/01_fachkonzept.md` §4 (release rules); `docs/03_service_vertrag.md` §2/§4/§5/§8; `docs/04_ui_spezifikation.md` §2/§3; backlog format `docs/06_backlog.md`; demo `docs/08_demo_szenarien.md`.

## Contract changes (all in this plan; docs/03 is updated in the same commits)

1. New stored element `Requests.waitingSince : Timestamp` (`@readonly`), new CSV column; set to `now` by every step whose result changes `status_code`, `inClarification` or `released` (03 §5.1).
2. New virtual elements `waitingText : String(40)`, `nextStep : StepCode`, `nextStepText : String(60)` (`@Core.Computed`, never written, computed per user and locale).
3. New calculated elements `priority : Integer` (ERROR 1, OPEN 2, REJECTED 3, DONE 4) and `rowCriticality : Integer` (ERROR → 1, else orderExists → 5, else 0), both `@readonly`, filterable/sortable.
4. Removed element `orderCriticality` (W-3).
5. `Capabilities.SortRestrictions.NonSortableProperties` and `FilterRestrictions.NonFilterableProperties` = `[waitingText, nextStep, nextStepText]` on `Requests`.
6. `Common.SideEffects` of all 11 step actions extended by `in/waitingSince, in/waitingText, in/nextStep, in/nextStepText, in/priority, in/rowCriticality, in/releaseReason, in/releaseLimit`.
7. Contract annotations (`srv/monitor-annotations.cds`): `@UI.Hidden` on `rowCriticality`, `nextStep`; `@UI.HiddenFilter` on `waitingText`, `nextStepText`; labels for the new visible elements.
8. New service texts (`_i18n/messages*.properties`): `WAITING_NOW`, `WAITING_MINUTES`, `WAITING_HOURS`, `WAITING_DAY`, `WAITING_DAYS`.
9. New stored elements `Requests.releaseReason : String(20)` and `releaseLimit : Decimal(15,2)` (`@readonly`), unmanaged association `releaseReasonRef`, new code-list entity `ReleaseReasons { key code : String(20); text : localized String(60) }` exposed `@readonly`; `Common.Text`/`TextArrangement #TextOnly` + fixed-value `ValueList` on `releaseReason`; `@Measures.ISOCurrency: currency` on `releaseLimit`. `checkRelease` now returns `{ released, releaseProcedure, releaseReason, releaseLimit }`; `RELEASE` sets `releaseReason = 'MANUAL'`; `CNG_NEW` overwrites both (03 §5.2).

## Risks

- **CAP response to `$filter=waitingText eq 'x'`** (virtual element): expected 400, but the new DB layer may answer 500 ("no such column"). The Jest case asserts `status >= 400`; if it is 500, add a tiny `before READ` guard on `Requests` that rejects `$filter`/`$orderby` on virtual elements with 400 and tighten the test to 400 (see Task 1 step 5).
- **`$orderby=priority` on the draft-enabled union**: same mechanism as the existing `$orderby=statusCriticality` test (calculated on-read via `status`), so expected to work; Task 3's Jest case proves it before the UI depends on it.
- **Column widths**: three new columns (~31 rem) push the one-column layout beyond the ~91 rem documented in docs/04 §2.2; Tasks 4/5 set widths and document the new sum; if the table scrolls at 1,500 px, demote "Erstellt"/"Geändert" (and `releaseReason`, W-9) to `#Low`.
- **Counts cost**: `showCounts` issues one `$count` request per non-selected view on every Start (4 extra requests). Fine for < 10 requests/day; mention in docs/04.
- **Relative texts are computed at read time** with the server clock; the list does not tick. Documented in docs/04 §2.2 ("Stand beim Laden; Aktualisieren über Start").
- **Decimal representation in JSON**: CAP may serialise `releaseLimit` as a number or a string depending on the `IEEE754Compatible` format parameter; Jest compares with `Number(...)`.
